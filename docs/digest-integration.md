# Digest integration

Apply `migrations/0004_digest.sql` to the existing D1 database after 0001/0002. The "not wired" notes below are historical: the Root integration corrections section describes the shipped wiring. No real email was sent.

## Bindings and configuration

Extend the worker Env with the exported `DigestEnv` fields in `src/digest.ts`: existing `DB`, optional existing `AI`, secret `RESEND_API_KEY`, verified-domain sender `DIGEST_FROM` (for example `Puerto Rico News <digest@news.dev.pr>`), and a cryptographically random secret `DIGEST_TOKEN_SECRET` of at least 32 characters. Set secrets through Wrangler secrets, not source control. Preserve the token secret: rotating it invalidates unsubscribe links and requires a deliberate migration of hashes. Only `env.RESEND_API_KEY` supplies Resend authentication. Missing configuration returns `status: unavailable` without a DB write or send. Links always use `https://news.dev.pr`; request Host/Origin cannot select their destination.

## Worker routes and UI

Import `subscribe`, `confirm`, `unsubscribe`, `runDigest` from `./digest` in the worker entrypoint. These are backend functions, not Response handlers.

* POST `/digest/subscribe`: accept a body capped at 2 KB, validate string email and language (`es` or `en`), call `subscribe(env,email,language)`. Return 202 for `accepted`, 503 for `unavailable`, with the returned bilingual message. Never echo the submitted email. Reject oversized/non-JSON input without logging bodies. Use a same-origin POST form or JSON client with explicit consent: daily news at 6:30 AM AST; confirmation required. Add a language selector and pending/unavailable UI states. Do not claim an email was sent: eligibility/provider failures intentionally share the accepted message.
* GET `/digest/confirm?token=...`: pass the token to `confirm`; render its generic result. Invalid, expired and already confirmed links return the same result. Confirmation is idempotent; cancelled subscriptions cannot be reactivated by old links.
* GET `/digest/unsubscribe?token=...` and POST at that path: call `unsubscribe`. POST supports the standard one-click email header. Both return the generic result, with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. No third-party scripts/assets or analytics on token pages. GET cancellation is convenient but mail link scanners can trigger it.
* Do not expose runDigest as a public route. A protected internal retry job is acceptable.

Suppress URL query strings, request bodies, email addresses and provider errors from application/access/analytics logs for all these routes. Module code logs none. Infrastructure access logging needs separate configuration. Never persist raw confirmation tokens. Unsubscribe tokens are HMAC capabilities; only their hashes are stored, regenerated from subscriber UUID plus secret for outbound mail.

## Scheduling and bounded delivery

Add cron `30 10 * * *` (10:30 UTC = 6:30 AST, no daylight-saving adjustment). In the worker scheduled handler, call `ctx.waitUntil(runDigest(env, controller.scheduledTime))` only for that cron; retain ingestion scheduling separately. The timestamp fixes the previous-24-hour selection window. Approximately five news stories are selected from up to 300 newest candidates, newest source representatives first then recency fill. Reddit is excluded. The day snapshot is immutable, as are recipient language and sender, keeping retry payloads stable.

Each invocation handles at most 25 recipients by default, hard cap 50. For larger lists, invoke further bounded batches with the SAME scheduled timestamp through an authenticated queue/continuation or retry cron. A retry cron can compute today's UTC 10:30 timestamp after that time; never use a moving `Date.now()` as the cutoff across retries. There is no automatic continuation inside this module. Failed sends back off five minutes; leases last one minute; maximum five attempts. Keep a run within the lease duration (each send timeout is 15 seconds). Distinct recipients are sent sequentially. Confirmation sending has no automatic retry: the subscriber may request again after an hour, at most three requests per UTC day. Global cap: 100 eligible-shaped requests/day, without IP storage; distributed attackers can exhaust this budget (add an upstream challenge if needed). Active and unsubscribed addresses receive no repeated confirmation. Re-enrollment of cancelled addresses is intentionally unsupported pending a separate authenticated consent flow.

Durable `(day,subscriber)` uniqueness and sent state prevent repeated daily sends. Resend's idempotency key is `digest/day/subscriber`; ambiguous outcomes (timeouts, 5xx) return the row to `pending` with a five-minute-or-`Retry-After` lease and retry under the same key only within 23 hours of first attempt, below Resend's 24-hour retention. A `sending` row whose lease expired is crash recovery and resumes the same way, as do pre-idempotency `uncertain` rows. After that, manual reconciliation is needed; never blindly reset delivery rows. A definite 4xx rejection (other than 429) is terminal `failed`. Resend success means API acceptance, not inbox delivery. Recipient status is checked immediately before each outbound request. Cancellation before that check prevents delivery; cancellation after the request starts cannot recall mail already in flight. Every confirmation and digest includes text/HTML unsubscribe links and List-Unsubscribe headers.

## Translations and shared context

Cached translations are reused through existing `translated()`, including its original-text equality checks. English digests skip Spanish articles without a matching cached translation; they may contain fewer than five stories (or only the header/footer). Spanish digests retain original English-source stories, consistent with the site. No translation is invented and no translation AI runs for email rendering.

`src/importance.ts` exports `getImportance({DB,AI}, excerpt)`, `extractImportance(excerpt)`, `validateImportance(candidate,excerpt)` and the `Importance` shape. During ingestion after translation, call `getImportance` for original and cached English summaries of hero candidates; attach the returned data to the existing live-data view model for hero rendering. Render `.text` escaped, only when nonempty, with a label such as “Context from excerpt / Contexto del extracto”. Digest generation uses the same helper/cache. Never call AI from a page-view handler. Cache keys hash exact excerpt and policy version, so content changes invalidate automatically; no additional article schema is needed. Plan periodic pruning of old cache and rate-limit rows and a retention policy for subscriber PII; retain delivery tombstones while duplicate prevention is required.

The existing Workers AI model selects a sentence, but output must exactly match a complete excerpt sentence of at most 140 characters. This deliberately excludes paraphrased or speculative “why it matters” claims: factual entailment cannot be reliably validated here. Failures use the first complete short sentence verbatim. Missing, long or unsafe excerpts produce empty context, never an invented explanation. This is grounded context, not a causal analysis or verified fact-check of publishers' excerpts. The hero hook is documented only because existing files are outside this task's ownership.

## Resend reference and validation

Official docs consulted: [Send Email](https://resend.com/docs/api-reference/emails/send-email) specifies POST `/emails` and Bearer authentication; [Idempotency Keys](https://resend.com/docs/dashboard/emails/idempotency-keys) specifies `Idempotency-Key` and 24-hour retention. Fetch uses the REST API directly without new dependencies. Test fetch is mocked, never real delivery.

Run `npx vitest run test/digest.test.ts test/importance.test.ts`, `npm run typecheck`, `npm run build` (Wrangler dry run). Tests use Node 22's built-in SQLite against real migration SQL. Integration tests exercise pending/active/expired/cancelled state, hash storage, repeated confirmation, suppression, per-day delivery uniqueness, diverse selection, hostile HTML escaping, missing configuration, and rejected hallucination/cache behavior. Infrastructure routes, deployed D1, cron, mail domain verification and delivery webhooks require integration outside this change.

## Provider decision: Resend only (November 2026)

An earlier draft routed the digest through ImprovMX's Send API. That was removed and `send()` is again Resend-only (`POST https://api.resend.com/emails`, Bearer `RESEND_API_KEY`, stable `Idempotency-Key`, one-click `List-Unsubscribe` headers). ImprovMX's official guidance classes the shared account as transactional and prohibits newsletter-style bulk mail from it; a shared transactional account must never receive the daily digest, so no ImprovMX path remains in `src/digest.ts`. The installed `IMPROVMX_API_KEY` secret is unused by the digest (a regression test asserts that its presence alone enables nothing and that no confirmation or newsletter ever routes to ImprovMX). Resend retains the display-name `from` from `DIGEST_FROM`. Enabling the digest requires: `wrangler secret put RESEND_API_KEY`, a `DIGEST_FROM` domain verified inside Resend (`digest@news.dev.pr` needs Resend domain verification with its own DKIM/DMARC records — `digest@code.pr` was verified in ImprovMX, not Resend), and `DIGEST_ENABLED="true"`. Missing pieces keep `configured()` false, so subscriptions return 503 and the UI shows the unavailable notice; nothing is sent and no database rows change. Delivery-state semantics after the retry fix: `pending` (eligible; lease-gated), `sending` (claimed, lease 90 s, crash recovery by expired lease), `sent`, and `failed` (definite provider rejection); ambiguous outcomes never park a row permanently because the idempotency key makes retry duplicate-free within Resend's 24-hour retention.
